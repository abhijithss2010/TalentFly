# TalentFly Implementation Plan

## Purpose and baseline

This plan turns the [Resume–Job Description Gap Analyzer PRD](./PRD%20Resume%E2%80%93Job%20Description%20Gap%20Analyzer%20(PWA%20%2B%20Chrome%20Extension)%20(1).docx) into an incremental monorepo implementation. It incorporates the requested first release scope: a Firebase-hosted installable PWA, a Chrome extension that captures a job description and starts a comparison, local PDF/DOCX/PPTX resume storage, a run-detail page, Claude and Copilot provider selection, encrypted local API-key storage, role-based Google login, an install-count dashboard, build-version reporting, and GitHub Actions CI/CD.

The existing [Todo app](../Todo/README.md) is the implementation reference for npm workspaces, Firebase Hosting/Functions, NestJS, Google authentication, server-side email allowlisting, Firestore, and GitHub Actions. TalentFly must use its own Firebase project configuration and credentials; do not copy Todo's secrets or project IDs.

## Product and architecture decisions

1. **Monorepo and stack:** root `package.json` npm workspaces with independently versioned `client/` (React + TypeScript + Vite PWA), `extension/` (Chrome Manifest V3 + TypeScript), and `server/` (NestJS deployed as a Firebase HTTPS Cloud Function), following the Todo repository's workspace scripts and build-info conventions. Share only protocol/schema code where it genuinely prevents drift between extension and PWA.
2. **PWA hosting:** Firebase Hosting serves static PWA assets and client-side routes. Production and local-development origins must be explicit configuration, not discovered from arbitrary pages. Recommend separate Firebase dev and production projects, following Todo's isolation pattern.
3. **Local-first data:** Resume files and extracted text, captured job descriptions, comparison reports, and LLM settings stay in browser IndexedDB. They are not uploaded to TalentFly's backend. The user's chosen provider receives only the resume/job text needed for a requested comparison.
4. **Extension boundary:** The extension extracts visible job-posting content only after a user action, displays an editable preview, and relays validated messages. It never receives or stores the LLM key or resume file. The PWA is the only component that runs LLM requests.
5. **Resume formats:** Support PDF and DOCX from the PRD plus PPTX as explicitly requested. Verify text extraction and licensing/size constraints for the selected client-side parsers before committing to specific packages. Preserve original files locally and let users inspect parsed text.
6. **Run lifecycle:** Each comparison has a unique run ID. The extension sends captured job data and selected resume ID(s), receives status updates and the run ID, and opens a deep link to the PWA run detail page. Persist runs locally so the link remains useful after reload and without another LLM call.
7. **Authentication and RBAC:** Guests use the local app without signing in. Normal, admin, and super users sign in with Google; the backend maps their verified account to a role in a dedicated Firestore role/identity collection, with explicitly provisioned emails for normal access. A platform-aware keyboard sequence reveals the sign-in affordance (for example, `Cmd+Shift+A`, then `L` on macOS, with an equivalent Control shortcut elsewhere). This is discoverability only, not a security control. Firebase ID-token verification and server-side role/permission checks protect every non-public endpoint; roles and allowlists never ship in client code. Admin/super views are limited to server-held operational/aggregate data: local resumes, job descriptions, reports, and LLM keys are not visible to them.
8. **Install metrics and privacy exception:** A web app cannot reliably know how many people downloaded/installed it, and an extension cannot infer installs from PWA Hosting. Define the dashboard metric as **distinct first-party app installations that have opened the PWA and reported**, not people or raw downloads. Use a random per-install UUID stored locally (not a hardware ID or fingerprint); disclose the report and collect only the minimum fields. Chrome Web Store download/install counts, if needed, come from its publisher reporting and are separate. This telemetry and the admin/auth calls are explicit exceptions to the PRD's “only LLM outbound request/no telemetry” rule; resolve consent, retention, and whether reporting is opt-in before enabling production collection.
9. **Provider scope:** Let users choose between Claude and Copilot and enter the credential required by the selected provider. Route each request through the matching provider adapter; never send a key or resume data to the other provider or TalentFly's server. Verify which Copilot API/product and credential type are intended, its direct browser/CORS support, and provider terms before implementation; do not imply that a Copilot subscription automatically supplies a usable API key. Keep provider selection, validation, errors, and model settings explicit.
10. **Encrypted key storage:** Store provider credentials only in IndexedDB as ciphertext encrypted/decrypted with Web Crypto; never persist plaintext after use, log it, or send it to the extension/backend. Define the key-encryption/key-unlock strategy (for example, a user passphrase-derived key via PBKDF2 and AES-GCM), IV/salt handling, lock/clear behavior, and recovery limitations before implementation. Explain that encryption at rest does not protect against a compromised browser session/device or malicious same-origin code.
11. **LLM output safety:** Validate structured model output against a runtime schema, render it as text (never HTML), ground suggestions in the selected resume, and flag claims that the user must verify. Show a preview/notice of what will be sent before the first comparison.
12. **Build identity:** Use each workspace's `package.json` version plus the current Git commit SHA (and build time if useful) to generate build metadata for the server, PWA, and extension. A version API reports server build identity; the client combines that response with its own bundled identity and the extension's reported/bundled identity in a diagnostics/About view. Since extension releases can be ahead of or behind the hosted app, show unavailable/unknown rather than implying the server knows which extension build is installed.
13. **PWA design and brand:** Design the PWA as a desktop-style workspace with persistent sidebar navigation and a responsive narrow-screen alternative. Create a simple original TalentFly logo/mark and use consistent app icon, favicon, manifest/splash assets, extension branding, and purposeful loading/empty states.
14. **Testing policy:** Every workspace must have a real test command and meaningful tests from its initial scaffold onward. Any commit changing client, extension, shared protocol, or server behavior adds or updates tests. Before considering a change complete, run the focused tests and all three workspace suites (client, extension, and server); CI also always runs all three suites plus lint, type-check, and builds. Do not use placeholder `echo` test scripts.

## CI/CD and environments

- **Pull request CI:** install from the lockfile; lint and type-check all workspaces; run client, extension, and server test suites; build PWA, extension, and server; validate the extension manifest and ZIP contents; run secret scanning. No production credentials are available to PR jobs.
- **Local secret guard (planned commit 24):** Husky runs Gitleaks on staged changes before commit and fails closed if the scanner is missing. This complements, but does not replace, CI secret scanning; developers install the native Gitleaks executable and follow documented setup.
- **Required tests:** client, extension, and server each have a real test script from initial scaffolding. Every behavior-changing commit adds/updates tests and is locally verified by running all three workspace suites (and relevant focused tests); CI always executes all three. Test suites are never placeholder success scripts.
- **Artifacts:** retain a versioned PWA build and a reproducible, unpacked-directory ZIP for manual testing or Chrome Web Store submission. Include build/version metadata but no `.env`, API keys, service-account files, or source-only development config.
- **Firebase deploy:** use GitHub Environments and short-lived Google authentication where feasible (Workload Identity Federation preferred over a long-lived service-account key). Deploy the PWA to Hosting; deploy the NestJS HTTPS function, Firestore rules, and indexes only when those server pieces exist. Keep dev and production targets distinct.
- **Extension release:** CI can validate and package automatically. A protected manual workflow may upload/submit through the Chrome Web Store API after publisher account, extension ID, and API credentials are configured. Store approval is an external step; CI success is not equivalent to public availability.
- **Secrets:** Firebase client configuration values are public application configuration, not authorization secrets. Never place LLM keys, service-account JSON, allowlists, or store publisher credentials in source or public build artifacts. Store deploy/admin credentials in GitHub/Firebase secret managers.

## Important gates and unresolved decisions

Resolve these before the dependent production work; use the listed defaults to keep early scaffolding moving:

1. **PWA origin and extension handshake:** default to Firebase Hosting as the production PWA origin and localhost for development. Confirm the final domain and whether the extension talks directly to the PWA page or uses the PRD's content-script relay; lock down the exact-origin permission and message design before implementing commit 11.
2. **Backend-versus-local-only boundary:** backend exists only for hidden admin auth and explicitly approved aggregate install reporting. It must not receive resume contents, job descriptions, reports, or provider keys. If strict PRD “no backend/no telemetry” takes precedence, remove install reporting and use Chrome Web Store publisher statistics instead.
3. **Meaning and consent for counts:** approve first-launch reporting, opt-in/opt-out behavior, retention period, and dashboard wording. A random browser installation ID measures reported browser profiles, not people; browser clearing/reinstalling can change it.
4. **Copilot API details:** user selection supports Claude and Copilot, but identify the specific Copilot product/API, accepted key/token type, browser/CORS support, terms, and response/token metadata before implementation. A Copilot subscription may not itself provide an API credential usable by a browser app.
5. **Extension publication:** confirm Chrome Web Store account/ownership, extension ID, distribution audience (private/unlisted/public), and whether submission should be automated or left as a downloadable ZIP plus manual publisher-console action.
6. **PPTX support and limits:** decide allowed file size and which embedded content is supported; initial extraction should target slide text and clearly report that images/charts may not be parsed.
7. **Role permission matrix:** confirm exactly what normal, admin, and super users can view/manage, including whether super users can assign roles. Guests remain unauthenticated and local-only; no role grants access to local browser data belonging to another user.
8. **Key unlock UX:** confirm whether the Web Crypto encryption passphrase is requested on each session or derived from another user-held secret. There is intentionally no server-side recovery path for local keys.
9. **Comparison scope:** first release compares one selected resume per run by default; multi-resume comparisons may be enabled if output, latency, and cost are understandable. Avoid promising match-score accuracy as an objective hiring measure.

## First end-to-end release acceptance

- A clean install runs actual client, extension, and server test suites and builds all three workspaces in GitHub Actions.
- A user installs the PWA from Firebase Hosting; its app shell launches offline after first load and local data remains in IndexedDB.
- The PWA uses a desktop-style sidebar layout with a responsive small-screen alternative and consistent TalentFly logo/icon/splash/loading branding.
- A user uploads PDF, DOCX, or PPTX, sees extracted text, and selects a stored resume from the extension.
- The extension captures an editable job-description preview only after user action and sends only the validated text/metadata to the configured PWA.
- The PWA generates and persists a run ID, uses the selected Claude or Copilot adapter with that provider's locally held key, and saves a validated report. Provider keys are encrypted with Web Crypto before IndexedDB persistence.
- The extension receives run status and an actionable run link; opening it shows the report without spending tokens again.
- Guest use requires no login. The hidden Google sign-in is revealed by the keyboard sequence; normal/admin/super access is mapped server-side and every protected API enforces Firebase token verification and Firestore-backed RBAC.
- The version endpoint reports server package version and commit SHA; diagnostics display the PWA and extension build identities as well, without assuming independently released extension builds match the current server.
- Install reporting is disclosed and minimal, uses no hardware fingerprint, and reports a clearly labeled distinct-install count only after the approved consent decision.
- Firebase deployment and extension store submission are reproducible, protected release actions; CI never exposes production credentials to untrusted code.
